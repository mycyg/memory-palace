# MemoryPalace（メモリーパレス）

> AIコーディングエージェントに長期記憶(long-term memory)を持たせる。やったこと、踏んだ地雷、交わした約束を覚えている。

[中文](README.md) | [English](README.en.md) | **日本語**

[![License](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE) ![Python](https://img.shields.io/badge/python-3.10%2B-blue.svg) ![TypeScript](https://img.shields.io/badge/TypeScript-3178C6.svg) ![Tests](https://img.shields.io/badge/tests-passing-brightgreen.svg)

MemoryPalace はセッションを越えて生き続けるエージェント長期記憶システム——イベントに基づいてエージェントのグローバル記憶を構築する。**イベントは記憶の原子である**：あらゆる作業を「意図 → 行動 → 結果」の閉ループとして記録する。原文は不変、索引は再構築可能、整理はオフラインで実行され、注入は予算で制限される。

## これは何か

AIコーディングエージェントには持病がある。セッションを閉じると、全部忘れる。

昨日は午後いっぱいかけて直したバグに、今日もまったく同じようにハマる。三回言い聞かせたルールを、四回目もまた言い聞かせる羽目になる。先月試して行き詰まったやり方を、来週また嬉々として試そうとする。

MemoryPalace はこの持病を治す。導入すると:

- エージェントがやったことは全部、自動的に**イベント**として記録される。何をしようとしたか、何をしたか、結果はどうだったか
- 次に同じファイルを開いたとき、同じエラーに当たったとき、関係する過去の経緯が**自動的に目の前に浮かび上がる**。エージェントが「調べなきゃ」と覚えている必要はないし、あなたが指摘する必要もない
- あなたは何もしなくていい。メモを書く必要も、タグを付ける必要も、メンテナンスする必要もない。バックグラウンドで勝手に記録し、勝手に整理し、重要でないものは勝手に忘れていく

一言でいえば:**使うほどプロジェクトに詳しくなるエージェント記憶。**

## 仕組み(30秒でわかる)

1. **記録** ―― エージェントが作業する間、ファイルの編集、コマンドの実行、todoの更新――こうした行動がすべて自動的にイベントとして記録される。
2. **眠る** ―― セッションが終わると、バックグラウンドで「一眠り」する。断片的な記録をまとめて整理し、教訓を蒸留し、ついでに明日やりそうなことを推測しておく。
3. **想起** ―― 新しいセッションが始まると、昨日やり残した作業はもう机の上に用意されている。あるファイルを開けば、以前そこで失敗した経緯が自動的に浮かび上がる。

導入する前:

> あなた:学習ジョブを並列で走らせて
> エージェント:了解!(起動失敗:ポート競合――先月と同じ問題、また20分かけて調査)

導入した後:

> あなた:学習ジョブを並列で走らせて
> エージェント:(記憶が浮かび上がる――`[2026-07-14] 並列ジョブが同じポートを取り合って衝突、ジョブIDでずらして解決`)
> 了解、ポートはジョブIDでずらして割り当てるね――前にここで痛い目に遭ったから。

## クイックスタート

### Claude Code

```bash
pip install -e .
```

[examples/settings.json](examples/settings.json) にある4つの hooks を、プロジェクトの `.claude/settings.json`(またはグローバルな `~/.claude/settings.json`)にマージする。導入した時点で有効になる:

- `SessionStart` ―― 起動時に「ワーキングセット」(覚えておくべき1画面分)をエージェントに渡す。初回実行時に `.memory/` を自動生成、設定不要
- `PostToolUse` ―― 作業中に手がかりから過去の記憶を想起する(純粋なテーブル参照、ミリ秒オーダー、モデル呼び出しなし)
- `PreCompact` ―― コンテキスト圧縮の直前にイベントを救済してディスクに書き出す(バックグラウンド)
- `SessionEnd` ―― セッション終了後にバックグラウンドの整理をトリガーする

整理をもっと賢くしたい場合(結論の自動補完、教訓の蒸留)は、モデルを1つ設定するだけでいい。設定しなくても動く――その場合はルールのみのモードになる。プロジェクトルートの `.env` か `~/.claude/eventmem.env` に書く([.env.example](.env.example) を参照):

```bash
EVENTMEM_BASE_URL=https://api.anthropic.com   # 任何 Anthropic 兼容端点均可
EVENTMEM_API_KEY=sk-...
EVENTMEM_MODEL=claude-haiku-4-5-20251001      # 小模型足够
```

動作確認済みの互換エンドポイント:Anthropic公式、DeepSeek(`https://api.deepseek.com/anthropic`)。

### DeepSeek Harness(dsh)

```bash
dsh plugin --profile <name> add dsh-eventmem
```

ホスト側で `import eventmem` できることが必要(実際の書き込みと整理はPython側が担う)。設定項目と既知の制限は [dsh-plugin/README.md](dsh-plugin/README.md) を参照。

**二つのホストが同じ記憶を共有する**:昨日Claude Codeで踏んだ地雷は、今日dshで同じファイルを開いても同じように浮かび上がる。`.memory/` はプロジェクトに紐づき、ツールには紐づかない。

## 名前の由来

method of loci(記憶の場所法)は、2000年前からある記憶術だ。覚えたいものを、よく知っている道筋の決まった場所に一つずつ置いていく。後日その道を再び歩くと、その場所に着いた瞬間、置いたものが自然と思い出される。探す必要も、思い出そうとする必要もない――そこに着けば、もうそこにある。キケロは演説を覚えるのにこの技法を使い、今日の記憶力競技の選手たちはトランプ1組をまるごと覚えるのに同じ手法を使っている。

本システムは「場所」をファイルパス、エラーシグネチャ、todoの意図に置き換えただけだ。アンカーもトリガーも変わらない。

## なぜこの設計か:3つの立場

1. **完結イベントを最小単位とする。** ナレッジポイントは保存しない、chunkにも切らない。1イベント = 意図 → 行動 → 結果(done / abandoned / superseded)。自己完結していて、まとめて注入し、まとめて破棄できる――これがエピソード記憶(episodic memory)の最小単位だ。lesson はイベントから蒸留されるものであり、独立したモジュールではない。
2. **連想的な想起を優先し、検索は最後の手段とする――query型RAGに対する代替案。** 主な想起経路は、アンカーが引き金になる能動的な想起だ。特定のファイルを開く、特定のエラーに当たる、特定のtodoを始める――そのたびに該当する過去イベントの結論が自動的に現れる。エージェント自身が「何を調べるべきか」を知っている必要はない(落とし穴というものは、まさにハマるまでそこにあると気づけない)。アンカーは完全一致で照合し、embeddingもベクトルストアも使わない。queryによる検索は、明示的な過去の調査にのみ使う。
3. **漏れは許容し、膨張は許容しない(prefer misses over bloat)。** 注入はハードな予算で制約する(ワーキングセット1〜2kトークン、1回の想起につき3行まで、同一セッション内は重複させない)。漏れは自己修復する――漏れる→ミスが起きる→そのミスが記録される→次はインデックスに載っている。膨張は自己修復しない。

## 類似システムとの違い

比較されることが多い3つのシステムとの違いを、1行ずつ書く。

| 比較対象 | MemoryPalaceとの違い |
|---|---|
| query型RAG | 主な想起経路はアンカー起動型の能動的な想起(push)であり、query→embedding→top-k検索(pull)ではない。検索は明示的な調査のみに使う |
| MemGPT / Letta | モデルによる自律的なページングは行わない。注入は固定予算とワーキングセットで制約する |
| Mem0 / ファクトストア | 記憶の最小単位は「意図→行動→結果」の完結イベントであり、会話から抽出した個々の事実ではない |

## アーキテクチャ

```
┌─────────────────────────────────────────────────┐
│ L2 注入层（进上下文，固定预算）                     │
│   会话启动注入工作集 ＋ 行为流触发的联想浮现          │
├─────────────────────────────────────────────────┤
│ L1 索引层（派生，可整体重建）                       │
│   working-set / 全量单行索引 / 锚点倒排 / lesson 表 │
├─────────────────────────────────────────────────┤
│ L0 存储层（append-only，不可变）                   │
│   一事件一 markdown 文件，锚点指向对话原文           │
└─────────────────────────────────────────────────┘
```

書き込みと整理は分離している。セッション中は追記のみを行い、整理――宙に浮いたイベントのクローズ、結果の補完、教訓の蒸留、昇格と引退、インデックスとprefetchの再構築――はすべてオフラインのメモリ整理(memory consolidation)パイプラインが担う。軽整理はセッション終了ごとにバックグラウンドで実行し、深整理は未整理量が閾値に達したときに走る。整理が書き込むのは派生レイヤーとlessonフィールドだけなので、冪等でいつでも再実行できる。夢の中で失敗しても、日中の記憶はそのまま残っている。

設計の全文は [DESIGN.md](DESIGN.md)、実装の契約は [SPEC.md](SPEC.md) を参照。

## CLI

```
eventmem status                  # 事件数、open 数、积压量、索引年龄、未读 CLAUDE.md 建议
eventmem stats [--json]          # 评估指标：浮现采纳率、注入成本、重复踩坑、预取命中、分级计数
eventmem log [--tree|--since N|--kind K]   # 事件时间线视图
eventmem search <query> [--all]  # 兜底检索（BM25）；--all 附带搜归档层（不解包）
eventmem read <id>               # 事件全文；命中冻结事件时提示 thaw
eventmem trace <id>              # 对话原文指针
eventmem consolidate --light|--deep|--deep-if-dirty
eventmem rebuild                 # 全量重建索引（L1 可随时丢弃重建）
eventmem thaw <epoch|id>         # 解冻归档事件回活跃层
eventmem purge --before <date>   # 删除更早的冻结包（默认 --dry-run，需 --yes）
eventmem init                    # 手动建 .memory/ 骨架（通常不需要，hook 会自举）
```

## 診断

hookが最優先する規律はただ一つ、「ホストの通常のセッションを絶対に妨げない」ことだ。例外は常に静かに終了する。その代償として、障害が起きても気づけない。確認するコマンドは3つ:

```bash
eventmem status                                      # 包与数据是否正常
echo '{"cwd":"'$PWD'"}' | python3 -m eventmem.hooks.session_start   # 手动跑一个 hook 看输出
tail -20 .memory/log/eventmem.log                    # 护栏日志（hook 异常都在这里）
```

## v0.2の主な機能

完結イベント・3層アーキテクチャ・連想的な想起に加えて:

- **顕著性(salience)**:ルールが境界を引き、自己評価が初期値を出し、最後は証拠がものを言う――重要度は証拠(引用されたか、想起が採用/無視されたか、supersedeを引き起こしたか)から離線で再計算される派生量であり、決めるのは「記録するかどうか」ではなく「どの層に置くか」
- **負のフィードバック**:無視された想起は自動的に重みが下がり、悪い記憶は自然と沈んでいく
- **prefetch(先読み)**:整理の締めくくりで次のセッションの入り口を予測する(「次はXを」という前向きなマーカー、未完了イベントの関連物、モデルレベルの予測)。起動画面には最初から「次はこれをやりそう」という一言が乗っている
- **階層的な忘却**:hot → cold(インデックスから除外)→ frozen(四半期ごとのエポック要約(epoch summary)とアーカイブへの一括格納、ディスク使用量はおよそ1/5に)→ purge(手動のみ)。圧縮するのはアクセス構造であって情報ではない――アーカイブの中身は完全な原文のままで、`thaw` でいつでも解凍できる
- **粒度の自動調整**:断片化したイベントはグループ化し、粗すぎるイベントには仮想的な分割を入れる。すべてインデックス層で完結する
- **サブエージェントの帰属**:委任した作業は委任イベントとして記録され、両ホストで構造は同じ
- **プロジェクト横断の昇格**:移植可能性の判定と機密情報のスクラビングという2つのゲートを通過した lesson は、ユーザーレベルへ昇格できる
- **CLAUDE.mdへの提案**:繰り返し検証されたlessonは貼り付け可能な提案文を生成する。ユーザー自身のドキュメントを自動で書き換えることはない
- **機密情報のスクラビング**:7種類の秘密情報パターンを、書き込み前に検知して止める
- **評価用の計測**:想起・注入・prefetchのすべてをローカルのjsonlとして記録し、`eventmem stats` が指標を一括出力する

`.memory/` は人間が読めるmarkdownだ――ガラス張りだが、メンテナンスの義務はゼロ。見たいときはいつでも見られるし、見なくても動き続ける。
