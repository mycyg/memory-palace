# MemoryPalace（メモリーパレス）

> イベントベースのコーディングエージェント向け記憶システム。イベントを記憶の最小単位とし、ひとつの作業を「意図 → 行動 → 結果」の完結したループとして記録する。原文は不変、インデックスは再構築可能、整理はオフラインで実行し、注入は固定予算で制約する。

[中文](README.md) | [English](README.en.md) | **日本語**

[![License](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE) ![Python](https://img.shields.io/badge/python-3.10%2B-blue.svg) ![TypeScript](https://img.shields.io/badge/TypeScript-3178C6.svg) ![Tests](https://img.shields.io/badge/tests-passing-brightgreen.svg)

プロジェクト名は MemoryPalace になったが、パッケージ名は変えていない。Python パッケージは引き続き `eventmem`（`pyproject.toml` の `name = "eventmem"`、CLI のエントリーポイントも同名）、DeepSeek Harness 用プラグインは引き続き `dsh-eventmem`。

MemoryPalace は、セッションをまたいで持続する、LLM エージェントのための長期記憶(long-term memory for LLM agents)だ。履歴を圧縮して情報が失われる要約にする代わりに、ひとつひとつの作業をイミュータブルなイベント――エピソード記憶(episodic memory)の最小単位――として保持し、アンカーが引き金になる連想的な想起(associative surfacing)で呼び出す。注入は常に固定のコンテキスト予算で制約される。

## 名前の由来

MemoryPalace という名前は、記憶術の method of loci(場所法)から借りている。覚えたいものを、よく知っている道筋の決まった場所に一つずつ置いていき、後日その道を再び歩くと、その場所に来ただけで置いたものを自動的に思い出す――探しに行く必要はない。これは本システムの「アンカー起動型の想起」の、もっとも古典的な形そのものだ。手がかりは検索されるのではなく、その場所に着いたから記憶のほうから浮かび上がってくる。キケロは『弁論家について』(De Oratore)でこの技法の起源と使い方を記している。今日、記憶力競技会に出場する選手たちも、トランプ一組や長い数字の列を暗記するのに同じ場所法(空間的な符号化)を使っている。本システムは「場所」をファイルパス、エラーシグネチャ、todo の意図に置き換えただけで、アンカーもトリガーも同じ仕組みのままだ。

## 3つの立場

1. **完結したイベントを最小単位とする。** ナレッジポイントや chunk は保存しない。1 イベント = 意図 → 行動 → 結果(done / abandoned / superseded)。自己完結しており、まとめて注入し、まとめて破棄できる。lesson はイベントから蒸留されたものであり、独立したモジュールではない。
2. **連想的な想起を優先し、検索は最後の手段とする(query 型 RAG に対するアンチテーゼ)。** 主な想起経路は、アンカーが引き金になる能動的な想起だ。エージェントが特定のファイルを開く、特定のエラーに遭遇する、特定の todo を始める――そのたびに、該当する過去イベントの結論が 1 行、自動的にコンテキストへ現れる。エージェント自身が「何を調べるべきか」を知っている必要はない。アンカーは完全一致(ファイルパス / エラーシグネチャ / intent のトークン)で照合し、埋め込み(embedding)もベクトルストアも使わない。query による検索は、明示的な過去の調査にのみ使う。
3. **漏れは許容し、膨張は許容しない(prefer misses over bloat)。** 注入はハードな予算で制約する(ワーキングセット 1〜2k トークン、1 回の想起につき 3 行まで、同一セッション内は重複させない)。漏れは自己修復する――漏れる → ミスが起きる → そのミスが記録される → 次はインデックスに載っている。膨張は自己修復しない。

## 位置づけ

比較されることが多い 3 つのシステムとの違いを、1 行ずつ書く。

| 比較対象 | MemoryPalace との違い |
|---|---|
| query 型 RAG | 主な想起経路はアンカー起動型の能動的な想起(push)であり、query → embedding → top-k 検索(pull)ではない。検索は明示的な調査のみに使う |
| MemGPT / Letta | モデルによる自律的なページングは行わない。注入は固定予算とワーキングセットで制約する |
| Mem0 / ファクトストア | 記憶の最小単位は「意図 → 行動 → 結果」の完結イベントであり、会話から抽出した個々の事実ではない |

## アーキテクチャ

```
┌─────────────────────────────────────────────────┐
│ L2 注入层（进上下文，固定预算）                     │
│   会话启动注入工作集 ＋ 行为流触发的联想浮现          │
├─────────────────────────────────────────────────┤
│ L1 索引层（派生，可整体重建）                       │
│   working-set / 全量单行索引 / 锚点倒排 / lesson 表 │
├─────────────────────────────────────────────────┤
│ L0 存储层（append-only，不可变）                   │
│   一事件一 markdown 文件，锚点指向对话原文           │
└─────────────────────────────────────────────────┘
```

書き込みと整理(consolidation)は分離している。セッション中は追記(flush)のみを行い、整理――宙に浮いたイベントのクローズ、結果(outcome)の補完、lesson の蒸留、昇格/引退、インデックスと prefetch の再構築――はすべてオフラインで行う。軽整理はセッション終了ごとにバックグラウンドで実行し、深整理は未整理量が閾値に達したときに走る。整理が書き込むのは派生レイヤーと lesson フィールドだけなので、冪等でいつでも再実行できる。夢の中で失敗しても、日中の記憶はそのまま残っている。

設計の全文は [DESIGN.md](DESIGN.md)、実装の契約は [SPEC.md](SPEC.md) を参照。

## 二つのホスト、一つの記憶

同じ `.memory/` を、二つのホストが共有できる。

- **Claude Code** ―― Python の hooks(`SessionStart` / `PostToolUse` / `PreCompact` / `SessionEnd`)が読み書きする
- **DeepSeek Harness(dsh)** ―― ネイティブの Cordis プラグイン [`dsh-eventmem`](dsh-plugin/README.md)。B-lite アーキテクチャを採用し、TS が担うのは同期的なホットパス(想起のルックアップ、イベントの feed への転記)だけで、`.memory/` への書き込みとオフライン整理は同じ Python `eventmem` CLI に子プロセスとして委譲する。実装が二重化することはない

`.memory/` はプロジェクトに紐づき、ツールには紐づかない。昨日 Claude Code で踏んだ坑は、今日 dsh で同じファイルを開けば同じように浮かび上がる。逆も同じだ。二つのホストは同じイベントストア、同じアンカーの転置インデックス、同じ lesson テーブルを共有し、同一セッション内の重複排除セットも共有する。

## インストール

### Claude Code

```bash
pip install -e .
```

[examples/settings.json](examples/settings.json) の 4 つの hook を、プロジェクトの `.claude/settings.json`(またはグローバルな `~/.claude/settings.json`)にマージする。

- `SessionStart` ―― ワーキングセットを注入する。`.memory/` が存在しない場合は無設定のまま静かに自己初期化する(ゼロコンフィグ、導入した瞬間から記憶が積み上がり始める)
- `PostToolUse` ―― アンカー想起(純粋なテーブル参照、ミリ秒オーダーで LLM は呼ばない)
- `PreCompact` ―― 圧縮の直前に行う救済的な抽出(バックグラウンド)
- `SessionEnd` ―― 機械的な flush と、バックグラウンドでの軽整理(未整理量が閾値に達すれば深整理も)

LLM を使う工程(取りこぼしたイベントの抽出、outcome の補完、lesson の蒸留)はオプションの強化機能だ。Anthropic 互換エンドポイントを設定すれば有効になり、未設定ならルールのみのモードに自動で降格し、パイプライン自体はそのまま動き続ける。プロジェクトルートの `.env` か `~/.claude/eventmem.env` に設定する([.env.example](.env.example) を参照)。

```bash
EVENTMEM_BASE_URL=https://api.anthropic.com   # 任何 Anthropic 兼容端点均可
EVENTMEM_API_KEY=sk-...
EVENTMEM_MODEL=claude-haiku-4-5-20251001      # 小模型足够
```

動作確認済みの互換エンドポイント: Anthropic 公式、DeepSeek(`https://api.deepseek.com/anthropic`)。

### DeepSeek Harness(dsh)

```bash
dsh plugin --profile <name> add dsh-eventmem
```

ホスト側で `import eventmem` ができる Python ランタイムが必要(実際の書き込みと整理は Python 側が担う)。設定項目、Model Experience、既知の制限は [dsh-plugin/README.md](dsh-plugin/README.md) を参照。

## CLI

```
eventmem status                  # 事件数、open 数、脏量、索引年龄、未读 CLAUDE.md 建议
eventmem stats [--json]          # 评估指标：浮现采纳率、注入成本、重复踩坑、预取命中、分级计数
eventmem log [--tree|--since N|--kind K]   # 事件时间线视图
eventmem search <query> [--all]  # 兜底检索（BM25）；--all 附带搜归档层（不解包）
eventmem read <id>               # 事件全文；命中冻结事件时提示 thaw
eventmem trace <id>              # 对话原文指针
eventmem consolidate --light|--deep|--deep-if-dirty
eventmem rebuild                 # 全量重建索引（L1 可随时丢弃重建）
eventmem thaw <epoch|id>         # 解冻归档事件回活跃层
eventmem purge --before <date>   # 删除更早的冻结包（默认 --dry-run，需 --yes）
eventmem init                    # 手动建 .memory/ 骨架（通常不需要，hook 会自举）
```

## 診断

hook が最優先する規律は「ホストのセッションを絶対に妨げない」ことだ。例外は常に静かに終了し、サンプル設定の `2>/dev/null || true` はパッケージ自体が欠けていても握りつぶす。その代償として障害も無感になる。調査方法は次のとおり。

```bash
eventmem status                                      # 包与数据是否正常
echo '{"cwd":"'$PWD'"}' | python3 -m eventmem.hooks.session_start   # 手动跑一个 hook 看输出
tail -20 .memory/log/eventmem.log                    # 护栏日志（hook 异常都在这里）
```

## v0.2 の主な機能

v0.1 の完結イベント／3 層アーキテクチャ／連想的な想起に加えて。

- **顕著性(salience)**: ルールが境界を引き、自己評価が初期値を出し、最後は証拠がものを言う。重要度は派生量であり、深整理のたびに証拠(引用されたか、想起が採用/無視されたか、supersede を引き起こしたか)から再計算される。決めるのは「記録するかどうか」ではなく「どの層に置くか」
- **負のフィードバック**: 無視された想起は自動的に重みを下げられ、悪い記憶は自然と沈んでいく
- **prefetch(先読み)**: 整理の締めくくりで次のセッションの入り口を予測する(「次は:」という前向きなマーカー、open イベントの関連物、モデルによる予測)。ワーキングセットには未来時制の領域も含まれる
- **階層的な忘却**: hot → cold(インデックスから除外)→ frozen(四半期ごとのエポック要約とアーカイブへの一括格納、ディスク使用量はおよそ 1/5 に)→ purge(手動のみ)。圧縮するのはアクセス構造であって情報ではない――アーカイブの中身は完全な原文のままで、`thaw` でいつでも解凍できる
- **粒度の自動調整**: 断片化したイベントはグループ化し、粗すぎるイベントには仮想的な分割を入れる。すべてインデックス層で行い、L0 は不変のまま
- **サブエージェントの帰属**: 委任した呼び出しは委任イベントとして記録し、両ホストで構造は同じ
- **プロジェクト横断の昇格**: 移植可能性の判定と機密情報のスクラビングという 2 つのゲートを通過した lesson は、ユーザーレベルへ昇格できる
- **CLAUDE.md への提案**: 繰り返し検証された lesson は貼り付け可能な提案文を生成する。ユーザー自身のドキュメントを自動で書き換えることは決してない
- **機密情報のスクラビング**: 7 種類の秘密情報パターンを、L0 に書き込む前に検知して止める
- **評価用の計測**: 想起・注入・prefetch のすべてをローカルの jsonl として記録し、`eventmem stats` が 4 つの指標を出力する
